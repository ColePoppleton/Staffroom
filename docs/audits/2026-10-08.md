# Audit 2026-10-08 — before Phase 8

Run at commit `e927a50` (Phase 7 complete) in a clean worktree with an isolated config home
(`TEACHING_TOOLS_HOME=data/audit/home`), so nothing here touched the owner's real config,
sessions folder or resources folder. Every finding below cites a command, screenshot or file.
Scratch evidence lives under `data/audit/` (git-ignored): `cli_output.txt` (2,007 lines, every CLI
run verbatim), `probes_output` runs, `shots/*.png` (62 screenshots, both themes), `out/` (every
file the tools wrote), `fixtures/` (invented break-it inputs, marked FAKE, no names).

## 0. Purpose check

*A UK secondary computing teacher's weekly workflow, on their own machine, outputs carried into
school by hand, with no pupil data anywhere.*

The product does this. All ten tools run from the CLI and the launcher; tests (470 passed,
1 skipped), ruff, mypy and the import-linter contracts are green; the three engineering rules hold
(`uv run lint-imports`: 2 contracts kept). What the audit found is almost entirely about the
second half of the sentence: whether another teacher could install it, trust it, and find what it
produced. The context for this phase is that the project is being open-sourced under a new name
with `uv tool install` as the canonical install, so the audience changes from one owner to any
teacher.

## 2. Persona findings

Format: `[area] what happened → what the persona expected → evidence → severity`.

### 2.1 The owner, Sunday night, 40 minutes (mark a mock, do-now for Monday, a Parsons problem)

- **O1 [outputs]** A worksheet made from the launcher (no input file) was written to the process's
  current directory — the git checkout root. Running marks or quiz on the files in `examples/`
  wrote `marks_10x_max_distribution.csv`, `question_bank_kahoot.xlsx` etc. into `examples/`.
  → Expected: outputs in one predictable folder, told before pressing Run. → Evidence: `git status`
  after the screenshot run showed `binary_medium_s42.docx`, `binary_medium_s42_key.pdf` at the repo
  root and five untracked files in `examples/`; `core/paths.default_output_dir` returns `Path.cwd()`
  when there is no input and no configured folder; the launcher's cwd is the checkout. →
  **hurts** (and will bite harder for a `uv tool install` user whose cwd is wherever the terminal
  was).
- **O2 [marks]** The saved distribution chart follows the UI theme: with the dark theme the PNG the
  owner would paste into a department report has a near-black background.
  → Expected: a print-friendly chart whatever the app looks like. → Evidence:
  `data/audit/out/marks/marks_10x_max_distribution.png` (dark) vs
  `data/audit/out/marks_light/...png`; `tools/marks/__init__.py` passes `ctx.config.general.theme`
  to `distribution_chart`. → **hurts**.
- **O3 [marks]** No sanity checks on the marks themselves. A script scoring 7 on a question whose
  MAX is 5 is graded (200 %) with no warning; a MAX cell of 0 gives facility 0 and "hard, weak
  discriminator"; blank cells and text like `ab` (absent) count as 0 and drag the facility index
  down; applying the percent preset with `--unit raw` silently puts every boundary above the paper
  total. → Expected: a warning line for each, as the "no MAX row" case already does. → Evidence:
  `p_marks.py` output ("grades [[7, 3, 10.0, 200.0, '9'] ...] warnings []"); `cli_output.txt` lines
  270–307 (messy file: "paper total 15 (q1=0 …)" with no warning) and 417–432 (unit=raw: 0 scripts
  above D). → **hurts**: wrong analysis with a green status.
- **O4 [marks]** In an .xlsx markbook export the `MAX` flag sits in the first column, which is the
  name column; the identifier filter drops that column first, so the MAX row is graded as a script
  and the max marks are "observed". → Expected: the MAX row to be found before columns are dropped.
  → Evidence: `tt marks run fake_markbook.xlsx` → "dropped Surname, Forename … No max marks given …
  4 scripts" for a 3-script file (cli run at 10:55). → **hurts**.
- **O5 [marks]** 3,000 rows × 30 questions took 57 s (`discrimination()` recomputes `totals()` inside
  the sort key: O(n²)). 200 rows takes 2.3 s, so a class or a year group is fine. → **polish**.
- **O6 [parsons, bugs]** Print layout wastes paper: the Parsons sheet puts each block's number and
  code on separate lines, so a 12-line program with 3 distractors spills to a second page before the
  answer grid; the bugs sheet puts one 13-line variant per page (17 variants = 17 pages; the default
  4 = 4 pages). → Expected: boxed blocks to cut out, two or three variants a page. → Evidence:
  `out/parsons/year9_parsons_s7.pdf` (2 pages), `out/bugs/year9_bugs.pdf` (17 pages). → **hurts**.
- **O7 [quiz]** Kahoot export: the summary says "5 questions → …" but two short-answer questions
  were skipped ("too few distractors"), so the file has 3 rows; and borrowed distractors cross
  topics ("What is 1010 in denary?" offers `SMTP`, `1F`, `8`, `10`). → Evidence: `cli_output.txt`
  1576–1588 and 1834–1839; `p_quiz.py` "short answer row". → **hurts** (mildly embarrassing in front
  of a class).
- **O8 [classroom]** Works as designed: label required, copy made once and re-opened thereafter,
  diff shows the lesson edit, promote writes `year9_v2.py` then `year9_v3.py` and never overwrites.
  Promote of an unchanged copy still makes a new version. → **polish**.
- **O9 [shell]** `tt update --check` on a branch without an upstream fails with git's "ambiguous
  argument" text; with the new `dev`/`main` process the owner's checkout may sit on `dev` and the
  launcher's Update button will compare against `origin/dev`, not the released `main`. →
  Evidence: `cli_output.txt` 1946–1948. → **annoys** (owner-only, but the launcher stays).
- **O10 [usage]** `tt usage` reports "nothing recorded" after ~90 CLI runs; only the launcher's
  worker records runs, although CLAUDE.md says CLIs do too. → Evidence: lines 1942–1944. → **polish**.

- **H1 [marks, good]** Identifier columns are dropped on load and logged; the per-script table is
  on screen only and labelled "view only, never saved"; the saved CSVs contain aggregates only. The
  filter is broad (name/forename/surname/initials/candidate/UPN/email/class/form/set/group/DOB/
  photo/username and joined forms) — 65 plausible headers probed. **Good; keep.**
- **H2 [library]** The index copies the full text of whatever is in the resources folder into
  `library.db`. If that folder contains pupil work — completed assessment tasks are a common thing
  to keep — their text, including any names in header comments, is now in `~/.config`. The tool has
  no exclusion list and gives no warning. In the owner's own folder, 8 indexed files contain
  "candidate number" and 4 contain "surname" (counts only; most likely exam-task templates, but the
  tool cannot tell and neither can the HoD). → Expected: a clear statement of what is indexed, a way
  to exclude folders, and a warning at index time when a file looks like it holds identifiers. →
  **hurts** (this is the one place the "no pupil data" promise depends on the teacher's folder
  hygiene rather than on the code).
- **H3 [privacy filter]** Per-pupil *flag* columns are not identifiers and pass through: `SEN`,
  `PP`, `EAL`, `Gender`, `Target`, `Behaviour`, `FSM`, `Postcode`, `Adm No` (only `adno` is
  listed), `Reg`. `marks` ignores non-question columns and never saves rows, so nothing persists;
  but `hello` writes every surviving column back to disk with a Total, and the `TablePreview`
  shows them. → Evidence: privacy probe table in this audit's transcript. → **annoys** today;
  becomes **hurts** if `hello` stays in the shipped tool list (see C3).
- **H4 [runner]** Documented as "a convenience fence, not a security boundary" and it is:
  `os.system("echo pwned")` ran, a file was written to `/tmp`, `importlib.import_module("socket")`
  and `__import__("urllib.request")` bypass the AST check, a 2 GB allocation succeeded, and an
  output flood captured 658 MB of stdout in 2 s (the trace tool's print loop reached 227 MB RSS in
  its 10 s window). These are the teacher's own files, so the risk is a frozen Mac, not a breach. →
  Expected: a cap on captured output and the limitation written where a teacher will read it. →
  Evidence: runner probe output; `/usr/bin/time -l` on `tt trace make printloop.py`. → **hurts**
  (memory), **docs** (limits).
- **H5 [sessions]** `.origin.json` stores the lesson label; the UI says "not a class, not pupils, no
  names" but cannot enforce it — a label of `Y9 set 2 - names: x, y` was accepted. Acceptable: it is
  a 60-character line typed by the teacher; note it in the data statement. → **polish**.

### 2.4 A trainee teacher, weak Python (trace tables and bugs for Year 9)

- **T1 [trace, good]** The year9 trace is correct, step by step, with scope shown for the function
  call and the printed output in the right rows; the blank sheet and key split cleanly; the step cap
  is announced on the sheet. **Good.** The default columns include function locals (`w`, `h`) and a
  Scope column, which is more than a Year 9 table needs; `--vars` / the Variables field fixes it but
  the trainee would not know to. → **polish**.
- **T2 [trace]** A program that calls `input()` with the Inputs box empty "succeeds": green status,
  a one-row worksheet, and only the log says "ended with EOFError: EOF when reading a line". →
  Expected: a red message "the program asked for input: fill in the Inputs box". → Evidence:
  `cli_output.txt` 1126–1132 (exit 0). → **hurts**.
- **T3 [bugs, good]** Variants are exactly one mutation each, each is run so the key says crash /
  wrong output / no visible change, and tab-indented programs survive. **Good.** Variants that make
  "no visible change" are still issued (v1 and v9 on year9) — fine for discussion, but the sheet
  does not say so. → **polish**.
- **T4 [worksheet]** The keys are right where checked by hand (binary, two's complement, addition
  with overflow, shifts, RLE, Huffman, file sizes). But some questions are not ones a teacher would
  set: truth tables at "hard" produce `Q = (NOT B AND B) OR (A OR B)` (C unused) and
  `Q = (C XOR C) AND (NOT A AND NOT C)` (Q is 0 on every row); "medium" tables use NAND/NOR, which
  are not in OCR J277 or AQA 8525; Boolean simplification sets `Simplify: NOT NOT (B OR 0)` and
  `(C AND C) AND ((C AND C) OR B)`, and the key's steps cite generic letters (`absorption: A AND (A
  OR B) = A`) that are not the question's letters. The trainee cannot tell these from good
  questions. → Evidence: `out/worksheet/truth_tables_hard_s1.pdf`,
  `boolean_simplification_medium_s1_key.pdf`, `p_worksheet.py`. → **hurts** (trust in the key).
- **T5 [fade]** Asking for more versions than there are fadeable lines gives duplicate versions,
  two of them with no blanks at all (`steps=8` on a 2-line program → blanks 0,0,1,1,1,2,2,2); a file
  that is not valid Python is faded without complaint; `--ranges abc` reports `invalid literal for
  int() with base 10: 'abc'`. → Evidence: `p_fade_bugs.py`, `cli_output.txt` 1421–1434. →
  **annoys**.
- **T6 [pseudocode, good]** Python → ERL and AQA is faithful for the GCSE subset, round-trips, and
  everything outside the subset is listed, never dropped. Garbage in gives a clear "could not
  parse". **Good.** A `.txt` input is assumed to be OCR, so `to-ocr notes.txt` says "cannot
  translate from 'ocr' to 'ocr'". → **annoys**.
- **T7 [jargon]** "Facility", "Discrimination", "seed", "ERL" appear with no explanation in the
  panels; the help text on options is good where it exists. → **polish**, covered by docs (D1).

### 2.5 The good list (must survive any redesign)

1. The hard rule is enforced in code, once, for every table (`core/privacy` via `core/csvio`); marks
   never writes a row; the per-script table is labelled view-only.
2. Every tool has a working CLI and a panel generated from the same spec; `tt new` produced a tool
   whose tests pass and whose CLI runs without edits.
3. Sandboxed runs: an infinite loop is killed in the stated time and reported in plain words; a
   socket import is refused before running; the window stays responsive while a 10 s run happens.
4. Classroom never touches the original: byte-identical after open, promote never overwrites.
5. The house style: one header/footer across docx and PDF, keys split to a separate file, seed
   printed so a sheet can be regenerated.
6. Pseudocode's explicit "could not translate" list.
7. Quiz bank validation with line numbers; retrieval windows reported per week.
8. Both themes are readable on every panel at 1240×780 and at the 1040×680 minimum; no clipped
   text or unreadable contrast was found in 62 screenshots.
9. Tests, lint, types and import contracts all green; the boundary tests actually catch Qt in tools.
10. Office files are never parsed; the library opens them externally.

**The redesign (one, bounded):** Parsons and bugs sheet layout (decision #12, issue #22). Measurable failure today: a

on 4 pages. Replacement: Parsons blocks as boxed, numbered cut-out cells in two columns with the

## 4. Not doing (and why), so it is not re-proposed

| Proposal | Reason |
| --- | --- |
| Markbook/class-list import from SIMS, Arbor, Go4Schools, Class Charts; any "names" column kept for the teacher's convenience | Hard rule: no pupil data. The identifier filter stays unconditional. |
| Per-row grade export ("just a CSV of totals and grades for my markbook") | A row-per-script file is traceable to a pupil once it leaves the app. Marks stays aggregate-only. |
| Absence handling by *who* was absent | Pupil data. Instead (#2) blank cells become "excluded from facility" with a count, no identity. |
| Seating plans or groupings derived from marks | Hard rule. |
| Kahoot / Google Forms / OneNote API upload, cloud sync of outputs or sessions, any account | Outputs are carried by hand; no cloud, no accounts. Nothing changes here. |
| Built-in code editor | Thonny is the editor; classroom solves the overwrite problem. |
| AI-generated questions, marking or feedback | Needs cloud and produces unverifiable keys; the generators are property-tested for a reason. |
| A real sandbox (seccomp, containers, network namespaces) for the runner | These are the teacher's own files; cost is high and it would still not be a boundary on macOS. Cap output, document limits (#6, #9). |
| Windows/Linux builds, code signing, notarisation | Deferred by the owner. |
| Removing the thin launcher in favour of the package only | Owner decision: it stays for the owner. |
| YAML question banks | Markdown works; adding a dependency and a second format buys nothing. |
| LMC / sorting visualisers, exam-paper generator | Already declined in ROADMAP; the bank is not big enough for the latter. |
| Full A-level pseudocode coverage (try/with/f-strings/classes) | Explicit "could not translate" is the design; GCSE subset is the scope. Revisit if A-level use appears in `tt usage`. |
| Rewriting the shell as a web app / Tauri / Electron | No measured failure: 62 screenshots, both themes, two window sizes, all readable; no persona was blocked by the shell. |
| Bulk tag editing, tag taxonomies, library folder watching | No evidence anyone tags yet (0 tags in the owner's sidecar). Wait for usage. |
| Usage telemetry upload, crash reporting | Nothing leaves the machine. `tt usage` is local and that is the whole feature. |
| Hiding the `hello` *code* or deleting the scaffold | Keep it as the reference and template; only remove it from the teacher-facing list (#5). |
